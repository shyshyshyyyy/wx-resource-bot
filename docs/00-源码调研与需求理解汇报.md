## 二、关键结论（有 4 条和你的预期可能不一样，重点看）

### 结论 1：wxauto4 免费版「有」回调监听，差距比预想小

你之前的理解（也是我记忆里的旧信息）是「wxautox4 Plus 才有 `AddListenChat`/`StartListening`，免费 wxauto4 方法受限」。
我对 **41.1.7 实际装出来的包**做运行时内省，结果是：

```
wxauto4.Chat  : ChatInfo, Close, GetAllMessage, LoadMoreCache, SendFiles, SendMsg, Show, chat_type
wxauto4.WeChat: AddListenChat, ChatInfo, ChatWith, Close, GetAllMessage, GetAllSubWindow,
                GetMyInfo, GetSession, GetSubWindow, IsOnline, LoadMoreCache,
                RemoveListenChat, SendFiles, SendMsg, Show, ShutDown,
                StartListening, StopListening, SwitchToChat, SwitchToContact, chat_type, dir, path
```

`AddListenChat(nickname, callback)` 的签名与 wxautox4 **完全一致**。
也就是说：**回调式监听这条主链路，免费版就能跑**，「自适应」的代价比我原先估计的低很多。

> 注意：`wxauto4` 的官方 `.pyi` 里**没写**这几个方法（属于未公开能力），文档站也只在 wxautox4 章节标注 ✨。
> 我按"运行时存在"来设计，但**必须在真机实测一次**确认免费版没有隐藏的条数/时长限制。这条我会列为阶段一的验收项。

### 结论 6：💡 你的离线授权生成器，机制我已解析清楚，可直接接入

我找到 `F:\Desktop\授权码生成器\`（v1.1 onedir）和它的 `license_history.json`，另外在 `F:\下载\WxSearchBot\WxSearchBot\license.py` 找到了配套的**完整客户端验签实现**。实测解析：

```
授权码 = base64url(payload) + "." + base64url(RSA-2048 签名)

payload 解码示例："04AE-F3B8-B0DD-3E7D|1819162329"
                   ↑ 机器码            ↑ 到期时间戳(0=永久)
签名长度：256 字节 = RSA-2048（PKCS1v15 + SHA256）
```

机器码算法（6 因子 SHA256 前 16 位，格式 `XXXX-XXXX-XXXX-XXXX`）：
`MachineGuid` / 主板 UUID / CPU ID / 系统盘卷序列号 / ProductId+InstallDate / 主机名
—— 并且有 **`machine.lock` 容错**（强因子命中即沿用，换网卡/加硬盘不会掉授权）。

现成实现里还带了：**时间回拨检测**、**反调试**、**公钥 base64 整体反转混淆**、**三处持久化（config.json / 程序目录 / 用户级目录，升级免重激活）**。

**我打算直接复用这套**，不重新造。需要你确认两件事：
1. 是否**沿用同一对 RSA 密钥**（同一把签发器出的码，你这个新机器人也能用）—— 我倾向沿用，省一套工具
2. 授权码现在**没有产品标识字段**（payload 只有 `机器码|到期时间`），意味着同一套码能用于你所有软件，产品之间不隔离。要不要借这次机会加个 `product` 字段？（老码可继续兼容）

## 三、SiverWXbot_plus：哪些能抄，哪些不能

它是一个**很成熟的工程样本**，但定位是「AI 对话机器人」，和你的「资源搜索机器人」不是一回事。

### 值得直接借鉴（我会吸收进架构）

1. **监听初始化的「加完再校验 + 重试」套路**（`_add_listen_chat_once` → `_verify_initial_listeners` → `GetAllSubWindow` 比对）
   wxauto 系加监听**经常静默失败**，这套校验非常有价值，我会原样吸收。
2. **`WxResponse` 的成功判定**（`was_send_success`）：返回值可能是 `True`/`dict`/`WxResponse`，必须统一判定。
3. **回调致命错误标志 `callback_is_die`**：回调里抛异常后主循环能感知并停掉监听，避免"看起来在跑其实死了"。
4. **风控延迟 `human_delay()`**、**配置热重载**、**定时群发的 schedule 用法**。
5. **打包路径处理**：`resource_path()` 走 `_MEIPASS` 读内置资源，`base_dir()` 走 exe 同目录写用户数据——这正是你《补充规范》第 2 条要的东西。
6. 授权是 **Apache-2.0**，可以合法复用/改造，保留版权声明即可。

### 不能直接用的

1. **面板是 Flask Web，不是 PySide6**。这与《补充规范》"PySide6 + 单文件 exe"**直接冲突**（见下个问题）。
2. `wxbot_core.py` 顶层就 `from wxautox4 import WeChat`，**硬绑付费库**，没有回退空间——你要求的"自适应"必须重写这一层。
3. 大量 AI 对话、Prompt 管理、Dify/Coze/DusAPI、朋友圈、远程面板、邮件/Webhook 告警——**与本产品无关**，是纯负担。
4. 业务编排围绕"AI 回复"设计，我们需要的是"指令 → 搜索 → 转存 → 模板回复"，路由逻辑不一样。

**我的建议**：以它为**架构参考和工程经验来源**，核心代码自己写，不 fork。理由：fork 之后要删掉的东西比留下的多，且它的 wxautox4 硬绑定会污染我们的适配层设计。

## 四、对你 4 项新需求的理解

### 1. 网盘账号管理界面
- 每个网盘一条记录：`网盘类型 / 账号备注 / Cookie / 转存目标文件夹 / 启用开关`
- Cookie 落地必须加密（你规范第 5 条）
- 需要「Cookie 有效性一键检测」
- **待确认**：网盘类型列表是固定的 7 种，还是要能自定义增删？

### 2. 盘搜接口配置
- 接口地址（默认你的 `http://38.92.9.77:8888/api/search`，可改，兼容别人自建 pansou）
- 请求方式（GET/POST）、超时、重试、每页条数
- **启用搜索的网盘类型**：多选（夸克/百度/UC/阿里/迅雷/光鸭/移动）
- 「移动」的数据源问题待你定（见结论 4）

### 3. 消息模板配置
我理解成两层：

- **触发指令**：私聊直接发关键词 / 群内 `@机器人` / 前缀触发（如 `搜 三体`）三种开关；指令词可配（默认 `搜`、`找`、`转链`…）
- **流程模板**（每条都支持占位符）：

| 模板 | 触发时机 |
|---|---|
| 帮助 | 收到 `帮助`/`菜单` |
| 搜索中 / 排队中 | 命中指令，先回一条稳住用户 |
| 搜索结果 | 拿到转存后的链接 |
| 无结果 | 引擎返回空 |
| 引擎超时 / 报错 | 网络或接口异常 |
| 触发限流 | 分钟/小时/天上限 |
| 转链完成 | 文案转链成功，回新文案 |
| 转链部分失败 | 文案里某几条链接转存失败 |
| 未授权 / 授权过期 | 授权失效 |

占位符初拟：`{关键词} {标题} {网盘} {链接} {提取码} {数量} {耗时} {昵称} {时间}`。

### 4. 分享文案转链（我认为这是**最值钱也最危险**的功能）
我理解的链路：

```
收到一段别人的分享文案
  → 正则抽取全部网盘链接 + 提取码（标注各自网盘类型）
  → 逐条用对应网盘账号转存到「转存文件夹」
  → 生成我自己的分享链接（+ 提取码）
  → 用「转链后文案模板」重组整段文案（保留原文案的描述文字，只换链接）
  → 群发到配置的目标群/好友（走随机延迟 + 限流）
```

风险点我会重点处理：
- 文案里链接很多时，转存耗时可能几分钟 → 需要**异步 + 进度提示**，不能卡住监听线程
- 部分失败要能**部分成功返回**，而不是整单失败
- 这是**风控最敏感**的操作，延迟和频率默认值我会给得比搜索更保守

## 五、必须你拍板的 6 个问题（不回答我无法开工）

### Q1（最重要）面板形态：PySide6 桌面 exe 还是 Flask Web 面板？
- **A. PySide6 + 单文件 exe**（符合《补充规范》）—— 界面代码全部新写，工作量大，但交付物最干净、最像商品。
- **B. 沿用 Web 面板**（SiverWXbot 的 Flask，或 WxSearchBot 的 FastAPI）—— 能复用大量已写好的 UI，浏览器打开即用；但**不是单 exe**（要带 templates/静态资源/端口），与你的规范冲突。
- **C. 混合**：PySide6 外壳 + 内嵌浏览器加载本地 Web 面板 —— 兼顾但体积爆炸（+100MB），且单文件更难打。

补充一个事实：你**现有的两个同类产品都是 Web 面板**（一个 Flask、一个 FastAPI），说明这条路你跑通过；
但你的《补充规范》把「PySide6（LGPL 版权红线）+ 单文件 exe + 不弹黑窗」写成了强约束，且明确说要卖给第三方买家。

我倾向 **A**：既然是当商品卖，单 exe 双击即用是核心卖点，且规范已经定了。
但这条你要拍板，因为它决定了 UI 层是「重写」还是「复用」。

### Q2 转存引擎：用本地 6 盘引擎，还是走你服务器的转存 API？（原「从哪来」已有答案，问题变成用哪个）
- **A. 直接用本机已有的 `transfer/adapters.py`（quark/uc/xunlei/aliyun/baidu/guangya 6 盘）** —— 客户端直连网盘，**不依赖你的服务器**，买家断网也能转存；你把各盘 cookie 保存在本地（加密）。缺点是网盘接口改版要跟着维护。
- **B. 调你服务器上的转存 HTTP API**（心悦 xinyue 那套） —— 服务器端维护、更新方便，但买家强依赖你的服务器存活，且你的服务器要扛并发。
- **C. 双引擎可切换**（面板里选 `本地` / `远程`，像 WxSearchBot 现在的 `mode: local|remote|both` 那样）—— 我倾向这个，但工作量 +1。

我推荐 **A 起步，预留 B 的接口**。理由：A 已经有能跑的代码，且符合你规范里"不要重写核心逻辑"。

### Q3 「移动云盘」数据源怎么办？
补一个 pansou 插件 / 换接口 / 本期先不做（界面上先留着但置灰）。

### Q4 起点选哪个代码库？
- **A. 以 `F:\下载\WxSearchBot\WxSearchBot` 为起点** —— 分层干净（core/search/transfer/panel）、转存引擎现成、自适应层现成、授权现成。**只差把 Web 面板换成 PySide6 + 补文案转链。**（我推荐）

### Q5 wxautox4 授权怎么给买家？
